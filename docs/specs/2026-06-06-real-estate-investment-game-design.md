# 不動産投資シミュレーションゲーム 要件定義書

- 起票日: 2026-06-06
- ステータス: ドラフト (本書は brainstorming セッションで合意した内容のまま記載。技術スタックの一部論点は `~/.review-platform/real-estate-investment-game/main/decision/` に詳細あり)

---

## 1. 目的

不動産投資 (区分マンションを中心とした収益不動産) のキャッシュフロー感覚を、Web ブラウザ上で 5〜10 分の 1 セッションで体験できる軽量ゲームを開発する。プレイヤーは限られた初期資金で **50 年間 (= 10 ターン × 5 年)** の物件運用を行い、最終的な純資産を最大化することを目指す。1 ターンを長めに取ることで、社会人スタートからリタイア後までを丸ごとシミュレートした長期資産形成のイメージを掴んでもらう狙い。

学習だけでも娯楽だけでもなく **「現実的な計算ロジック + 適度な乱数イベント」のバランス型** とし、毎回少しずつ違う展開を楽しめるようにする。

## 2. ターゲット / 用途

- 不動産投資に興味があるが、実際に物件を持つ前にキャッシュフローや空室リスクの感覚を掴みたい人
- 開発者本人のフロントエンド学習・ポートフォリオ
- URL を共有して気軽に遊んでもらう用途

## 3. プラットフォーム

- **Web ブラウザ (PC / スマートフォン両対応)** とする。
- サーバサイドは持たない。静的ファイルとしてビルドし、GitHub Pages 等に置く構成。
- バックエンド・ログイン・スコア共有等は本バージョンではスコープ外。

### 採用理由

URL を共有するだけで誰でも遊べる手軽さに加え、スマートフォンでも触れるようにすることで隙間時間にもプレイしてもらえる想定。ネイティブアプリは配布・開発コストが高く「簡単に作る」方針に合わないため棄却。CLI は「ゲームらしさ」「他人と共有する楽しさ」が弱いため棄却。

(詳細: `decision/platform-web-pc-sp.md`)

## 4. ゲームコンセプト

### 4.1 トーン

**バランス型 (学習 + 適度な乱数)** とする。空室や修繕費といったリアルなイベントを乱数で起こしつつ、ロジック (利回り計算・ローン返済計算) は現実に近い式を使う。

#### 採用理由

純粋な学習特化だと計算式の確認に終始してゲームとして遊ぶ動機が弱く、完全なエンタメ寄りにすると不動産投資の学びが薄れる。両者のバランスを取った形が本ゲームの狙い。

(詳細: `decision/game-tone-balanced.md`)

### 4.2 セッションの長さとターン構造

- **1 セッション = 10 ターン**
- **1 ターン = 5 年** (= 1 セッション全体で 50 年)
- 想定プレイ時間: 5〜10 分
- 1 ターンの順序:
  1. ターン開始 (年が 5 年進む)
  2. 保有物件から家賃収入 (この 5 年分まとめて空室判定し、満室なら満額×5年・空室なら0円×5年)
  3. 保有物件のローン返済 (5 年分の元利均等返済額をまとめて現金から差し引く)
  4. 修繕イベントの判定 (この 5 年に 1 回判定。発生したら一時出費)
  5. プレイヤーアクション (購入 / 売却 / スキップ)
  6. 純資産の再計算とグラフ更新

#### 採用理由 (10ターン × 5年 = 50年)

「簡単なゲーム」の方針に合わせてターン数自体は 10 に抑えつつ、不動産投資の本質である長期 (=20〜30 年以上のスパン) を体感できるようにするため、1 ターンを 5 年に拡張した。10 ターン × 5 年 = 50 年 はサラリーマンの社会人キャリアをまるごとシミュレートする尺度で、ローン完済後の純資産形成の感覚も体験できる。

トレードオフとして、1 ターンで 5 年分の空室・修繕判定をまとめるため判定粒度はやや粗くなるが、長期スパンを優先した。判定粒度を 1 年単位に細かく回す案 (1 ターン内で 5 回ループ) は実装量が増えるため、本バージョンでは採用しない。

### 4.3 プレイ形式

**1 人プレイ (シングルプレイヤー)** とする。同時複数人プレイ・ホットシート方式・オンライン対戦は本バージョンでは扱わない。

#### 採用理由

サーバを持たずにフロントエンドだけで完結させたいため。シングルプレイなら状態管理がシンプルで、URL を開けば誰でもすぐ遊べる体験を維持できる。

### 4.4 勝敗条件 / スコア

- **10 ターン終了時の「純資産」を最大化する** ことが目的。
- 純資産 = 現金残高 + 保有物件評価額の合計 − ローン残高の合計
- 数値勝負のみ。クリア / ゲームオーバーの概念は持たない。途中で現金残高がマイナスになっても (ローン返済や修繕費を払えなくても) ゲームは強制終了しない。純資産がその分下がるだけで、10 ターン目まで遊び続けられる。
- スコアの保存・ランキングは行わない (リロードで消える)。

#### 採用理由

「目標額達成」「サバイバル」よりも 1 軸の数値でシンプルに評価する方が、初プレイのプレイヤーに分かりやすい。複合スコア (キャッシュフロー安定性等) は説明コストが増えるため棄却。

### 4.5 物件モデル

- **1 物件 = 1 部屋 (区分マンション中心の単一物件カード方式)** とする。
- 1 物件のパラメータ:
  - 物件名 / 所在地ラベル
  - 価格 (購入時)
  - 月家賃 (満室時)
  - 想定利回り (満室想定の表面利回り; 表示用)
  - **年間空室率 (連続値, 0.004〜0.05 (= 0.4%〜5%))**: 物件生成時に乱数で決まり、以後固定。家賃収入計算に「(1 − 空室率)」として連続適用する
  - 修繕リスク係数 (毎ターン修繕費発生確率と金額幅に影響)
  - 評価額 (時価; 本バージョンでは購入価格固定で減価なし)

#### 採用理由

10 ターンのショートスコープにおいて、1 棟物件 / 戸建て / 複数タイプ混在は計算項目とバランス調整が重くなる。区分マンション 1 物件カード方式なら、家賃 × (1 − 空室率) × 12 ヶ月 のような分かりやすい式で説明でき、ゲーム的にも比較しやすい。

### 4.6 ローン (借入)

- **シンプルローン (固定利率 + 元利均等返済)** を採用する。
- 物件購入時にローンを自動で組む。
- 利率・返済年数はゲーム内固定値 (例: 利率 2.0% / 返済 35 年) で扱い、変動なし。
- 1 ターン = 5 年なので、毎ターンの返済額は元利均等返済の月額 × 12 ヶ月 × 5 年で固定。
- 35 年ローンは 7 ターン目 (= 35 年経過時点) に完済予定。完済後のターンはローン返済額が 0 になる。
- 中途売却時はローン残高を全額一括返済する。
- 繰り上げ返済の手動操作は持たない。

#### 採用理由

不動産投資の学習体験としてレバレッジ (借入で物件を持つ) の感覚は必須。一方で「現金 or ローン選択」「繰り上げ返済」を入れると UI とロジックが複雑化するため、最小実装としてローン強制 + 固定パラメータを採用。

### 4.7 ターン中のアクション

各ターン、プレイヤーは以下のいずれか 1 つを実行できる:

| アクション | 内容 |
|---|---|
| **購入** | 提示された購入候補から 1 物件を選び、ローンを組んで取得 |
| **売却** | 保有物件から 1 物件を選び、評価額で現金化 (ローン残高は一括返済) |
| **スキップ** | 何もしない (家賃収入とローン返済だけが発生) |

#### 採用理由

「購入 + 売却 + スキップ」で「いつ買って、いつ出口を取るか」という不動産投資の核となる意思決定を体験できる。繰り上げ返済等のアクションは UI 要素が増えるため、初回バージョンでは入れない。

### 4.8 ランダムイベント

家賃収入の不確実性と修繕費の発生をモデル化する。金利変動・地価変動・災害カード・税制改正等は本バージョンでは扱わない。

- **空室率による収入減 (連続値モデル)**: 物件ごとに生成時点で年間空室率 (0.4%〜5%) が決まり、以後ゲーム終了まで固定。各ターンの家賃収入は次式で計算する。

  ```
  ターンあたり家賃収入 = 月家賃 × 12 × 5 × (1 − 年間空室率)
  ```

  RENOSY が公開している入居率実績 99.6% (= 空室率約 0.4% / 2025 年 10 月時点) を空室率レンジの下限値として採用し、物件品質の差を上限 5% まで表現する。2 値判定 (満室 or 完全空室) ではなく連続値モデルを採用した理由は、RENOSY の「平均空室期間 18〜27 日」という実績が「ほぼ満室・たまに数日空き」という連続的な状態を表しており、2 値判定だと再現できないため。

- **修繕費 (確率的発生)**: 物件ごとに修繕リスク係数に基づき毎ターン (= 5 年に 1 回) 確率発生。発生時は一定範囲の修繕費が現金から差し引かれる。空室と異なり、こちらは確率発生型のイベントとして残る。

#### 採用理由

「空室と修繕」は不動産投資の代表的なリスクなので必須。一方、災害カードや金利変動を入れるとバランス調整工数が大幅に増えるため、初回バージョンでは見送り。

## 5. UI 構成

### 5.1 全体方針

- **現バージョン (v1)**: シンプル (テーブル中心 + 最低限のグラフ)。アニメーション・サウンド・装飾画像は持たない。スマートフォンでも読めるレスポンシブレイアウト。
- **最終目標 (v2 以降)**: **ドット絵 + 可愛らしい RPG 風 UI** に置き換える。プレイヤーをドット絵キャラクター、物件をタイル/スプライトで表現し、メニューやステータスウィンドウも昔ながらの RPG (例: ドラクエ / ファミコン世代の RPG) を意識した枠デザインに刷新する。v1 のテーブル UI はあくまで「ロジックが正しく動くことを最短で確認する」ためのプロトタイプ位置付け。

v1 を開発する際の留意:

- ロジック (`src/lib/`) と表示 (`src/components/`) を完全に分離して書く。これにより v2 で見た目を全面刷新しても、計算ロジックは流用できる。
- CSS は Linaria でコンポーネントごとに閉じ込め、v2 への置き換え時に影響範囲を局所化する。
- v1 で凝ったテーブル装飾を入れない (v2 でどうせ捨てるため)。

### 5.2 画面構成 (単一画面 SPA)

```
┌─────────────────────────────────────────┐
│ ヘッダー: ターン X / 10  |  現金 ¥XX  |  純資産 ¥XX │
├─────────────────────────────────────────┤
│ ┌─────────────┬─────────────┐           │
│ │ 保有物件テーブル │ 純資産推移グラフ │       │
│ │ ・物件名      │ (折れ線, 横軸=ターン) │   │
│ │ ・家賃 / 残債  │              │           │
│ │ ・評価額      │              │           │
│ └─────────────┴─────────────┘           │
├─────────────────────────────────────────┤
│ 購入候補テーブル                            │
│ ・物件名 / 価格 / 月家賃 / 利回り / 空室率   │
│ → 各行に「購入」ボタン                       │
├─────────────────────────────────────────┤
│ アクションパネル                            │
│ [ 売却 ▼ ] [ 次のターンへ (スキップ) ]      │
└─────────────────────────────────────────┘
```

- スマートフォン時は縦積み (保有物件 → グラフ → 購入候補 → アクション) に切り替える。

#### 採用理由

カード UI やリッチビジュアルは見栄えが良い反面、実装量が増える。テーブル中心であれば数値比較がしやすく、不動産投資シミュレーションのねらいに合致する。

### 5.3 永続化

スコア・プレイ履歴の保存は **行わない**。リロード / タブを閉じればゲームは消える。

#### 採用理由

シングルプレイの軽量ゲームに過剰機能を入れないため。ランキング機能を入れるとサーバが必要になり、スコープが大きく広がる。

## 6. 数値設計 (初期値の暫定案)

実装時に調整する想定の暫定値。バランス調整は本要件外の作業として行う。

| パラメータ | 暫定値 |
|---|---|
| プレイヤー初期所持金 | ¥10,000,000 (1,000 万円) |
| 1 ターンの年数 | 5 年 |
| 1 セッションのターン数 | 10 ターン (= 50 年) |
| ローン利率 | 2.0% / 年 |
| ローン返済期間 | 35 年 (元利均等) |
| 各ターン提示される購入候補数 | 3 件 |
| 物件価格レンジ | ¥10M〜¥40M |
| 月家賃レンジ | 物件価格に対して年利回り 4%〜10% |
| 年間空室率レンジ | 0.4%〜5% (RENOSY の入居率実績 99.6% = 空室率 0.4% を下限。出典: https://www.renosy.com/) |
| 修繕発生確率 / ターン (= 5年に 1 回) | 5%〜20% |
| 修繕費レンジ / 回 | ¥100,000〜¥1,000,000 |

物件のパラメータは決定的ではなく、毎ターン乱数で生成する (例: 価格に対する利回りや空室率を一定範囲でランダム化)。

## 7. 技術スタック

最小構成。GA 社内の他リポジトリ `renosy_lp_inquiry_chat` とコア + 開発体験ツールを揃える方針で、サーバ関連系は除外する。

| カテゴリ | 採用ライブラリ |
|---|---|
| ランタイム | Node.js 24.1.0 (renosy の `.node-version` と一致) |
| ビルド / 開発サーバ | Vite 6 |
| UI フレームワーク | React 19 |
| 言語 | TypeScript 5 |
| スタイル | Linaria (build-time CSS-in-JS) |
| テスト | Vitest |
| Lint + Format | Biome |
| Git hooks | Lefthook |

### 入れないもの (renosy にあるが今回不要)

- Storybook / ESLint / Stylelint / markuplint (Biome に集約)
- React Hook Form / Valibot (フォーム要素なし)
- TanStack Query / MSW (サーバ通信なし)
- Rollbar (本番監視は過剰)
- CircleCI / GitHub Actions (CI/CD なし)

### 採用理由 (要約)

- コア (Vite + React + TS) を選んだ理由: 数値ロジックを型で守れる / 複数 UI 部品をコンポーネントに分割できる / 静的デプロイが容易 / モダンFEを学べる (詳細: `decision/tech-stack-vite-react-ts.md`)
- renosy と揃えつつ最小化した理由: 軽いゲーム開発スコープに合わせる + 脱スタックガチャを避けて他リポとの上下移動・知識再利用をしやすくしたい (詳細: `decision/tech-stack-libraries-aligned-with-renosy.md`)

## 9. 非機能要件

- **ブラウザ対応**: 最新の Chrome / Safari / Firefox / Edge。Internet Explorer は対象外。
- **レスポンシブ**: PC (>= 1024px) / SP (375px〜) で読みやすい。タブレットは特別対応しない (PC レイアウトが流れて表示される程度で良い)。
- **アクセシビリティ**: テーブル要素は意味的にマークアップする (`<table><thead>` 等)。スクリーンリーダ完全対応は本バージョンではスコープ外。
- **パフォーマンス**: 計算ロジックは純粋関数で 1 ターン処理が体感的に即時 (< 100ms) であること。

## 10. スコープ外 (将来の拡張候補)

将来検討するかもしれないが、本バージョンでは含まないもの。

- **ドット絵スプライト + RPG 風メニュー UI への全面刷新** (本ゲームの最終ビジュアル目標。v1 のテーブル UI を置き換える)
- ランキング / スコア共有
- マルチプレイ
- ホットシート
- 物件タイプの多様化 (一棟・戸建て・REIT 等)
- 災害イベント・金利変動・地価変動・税制改正
- 繰り上げ返済 / リファイナンス
- セーブ・ロード
- アニメーション / サウンド (BGM・効果音)
- 多言語対応

## 11. 受け入れ条件 (Acceptance Criteria)

- [ ] 1 セッション (10 ターン) を最後までプレイでき、最終純資産がスコアとして表示される
- [ ] 各ターンで「購入 / 売却 / スキップ」のいずれかを選択できる
- [ ] 購入時、対象物件のローンが自動で組まれ、ローン残高が記録される
- [ ] 売却時、対象物件のローン残高が一括返済され、差額が現金に反映される
- [ ] 各ターンで保有物件の空室判定・修繕判定が発生し、家賃収入・現金残高に反映される
- [ ] 純資産の推移が折れ線グラフで可視化される
- [ ] PC とスマートフォンの両方で操作可能なレイアウト
- [ ] 利回り計算・ローン返済計算など純粋関数のユニットテストが Vitest で通る
